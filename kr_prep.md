# Подготовка к контрольной работе

## 1. Когда я выберу rebase, а когда merge? Почему?
- **Rebase** — для работы в локальной feature-ветке перед интеграцией в main. Это позволяет подтянуть свежие изменения из main и получить чистую линейную историю без лишних merge-коммитов.
- **Merge** — при слиянии готовой feature-ветки в общую публичную ветку (main/develop) и для командных веток, чтобы сохранить подлинную историю параллельной разработки и не переписывать историю.

## 2. Что произойдёт, если я сделаю rebase публичной ветки, с которой работают коллеги?
Перепишутся хеши всех коммитов начиная с точки rebase. У коллег возникнет расхождение локальной ветки с удалённой: последующий pull создаст массу конфликтов, задвоение коммитов и риск потери актуальных изменений.

## 3. Зачем нужен multi-remote и в каких реальных сценариях он применяется?
Multi-remote позволяет локальному репозиторию работать с несколькими серверами. Реальные сценарии:
1. Автоматическая репликация / бэкап-зеркало (например, синхронизация GitHub и GitLab).
2. Модель Forking Workflow в Open Source (remote origin — свой форк, remote upstream — исходный проект).
3. Плавная миграция с одного Git-хостинга на другой без остановки разработки.
